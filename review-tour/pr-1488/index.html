Report a merge gate status on every PR

2 stops2 questions152 of 635 changed lines on the tour

The problem

Every PR waits for the owner's approval, so the median PR waits 7.8 hours from open to merge (last 98 PRs), and stacked slices wait one review session each. Most of those PRs change nothing the owner wants to judge: rules are trusted to the agent and the rules checker, and only screen looks and behaviour need a person.

What changes

A new check, gate, decides per PR whether it needs the owner. The owner's approval of the current commit always passes it. A PR that changes a screenshot golden, or anything that decides what the gate lets through (workflows, the gate's code, CLAUDE.md, REVIEW.md, .claude/), waits for the owner and gets the needs-owner label. Any other PR passes once the session posts a passing review verdict for its head commit, and, when it changes engine, scenario or card data code, a passing rules check too. The gate runs from main only and posts as its own GitHub App, so a PR can't change or fake the gate that judges it.

Questions for you

  1. Is a changed screenshot golden the right signal for 'needs the owner'? A UI change with no new picture is sent back to the agent by the reviewer instead, since coding guidelines §3 require one.

    Concerns stop 1. Picked: Goldens plus the gate's own files.

  2. For MA.3 the gate needs its own GitHub App (commit statuses: write) with MERGE_GATE_APP_ID and MERGE_GATE_PRIVATE_KEY in a merge-gate environment limited to main. The PR bot's key can't be used, because any PR workflow can read repository secrets. OK to set that up when MA.3 comes?

    Concerns stop 2.

Who decides

The owner's latest approval or rejection wins, but an approval counts only for the commit it was given on. Then the owner's paths, then the session's newest verdict for the head commit, and the rules check when rule code changed.

2Workflow

Running from main, posting as the gate's App

Every trigger runs the default branch's copy: reviews come in through workflow_run, since pull_request_review would run the PR's own copy. The status is posted with a key that only main can read.

How we know it works

  • An approval of an older commit doesn't pass a later push.

    Checked by gate.test.ts › an approval of an older commit does not pass a later push

  • Goldens, workflows, the gate's code, CLAUDE.md, REVIEW.md and .claude/ always go to the owner, even with a passing verdict.

    Checked by gate.test.ts › sends $file to the owner even with a passing verdict

  • A verdict counts only for the head commit and from the owner's account or the PR bot; a newer failing one wins.

    Checked by gate.test.ts › a test-only PR with $name: $kind

  • Rule code needs the rules checker's pass; 'none' blocks like 'fail'.

    Checked by gate.test.ts › a PR changing rule code with rules "$rules": $kind
