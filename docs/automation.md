### Screencasts

UI changes are easier to review as a recording than as a diff. E2E specs tagged `@flow` (`test('…', { tag: '@flow' }, …)`) are re-run by the `screencast` Playwright project with `slowMo` of 250 ms and video on, with a pointer and a highlight drawn on every interaction and the current `test.step` name as a caption (`video.show`, `pnpm e2e:screencast`). `apps/web/scripts/screencast/cli.ts` converts each passing flow into a GIF (one frame per 250 ms step, each held 4 times as long, so it plays 4× slower than recorded; 800 px wide) plus the original WebM, adds a player page (`player.html`, with this push's flows written in, so its link can only pick one of them and never names a URL) that plays the WebM with pause, step-wise seeking and a speed choice starting at 0.25×, and renders the Markdown section, which shows the GIF and links the player; the preview workflow publishes them under `pr-preview/pr-<n>/screencasts/` and replaces the section between `<!-- screencasts:start -->` and `<!-- screencasts:end -->` in the PR description (appending it if the markers are missing). Text outside the markers is never touched. Specs tagged `@shot` (`apps/web/e2e/shots/`) run in the same command in the `screenshot` Playwright project, at full speed and without video, with `screenshot: 'on'`, so Playwright photographs each one as it ends; `cli.ts` copies the passing ones next to the GIFs and the section shows them under "Screenshots", above the screencasts (`RECORDING_PROJECTS` names the two projects, so each spec is read from its own). Each PR tags only the flows that show its own change (`docs/coding-guidelines.md` §3), and the workflow enforces it: it also runs the base commit's tagged specs (in a worktree of the merge commit's first parent, with its own install), and `cli.ts` leaves out every spec whose last picture is the same on both sides (a shot's picture, a flow's end state, which the `screencast` project photographs too; compared with `pixelmatch` at Playwright's default tolerance, since the playmat's faint lines differ by a few pixels between runs). So tags earlier PRs left on `main` show only when this PR changes their picture, and a flow whose only change is in its middle is not caught. The section links its pictures (GIFs and PNGs) from the gh-pages commit just pushed on `raw.githubusercontent.com` (a commit, since the raw host caches branch URLs for 5 minutes whatever their query string), which serves them as soon as the workflow has pushed, so the description is updated right away instead of after the Pages build (a minute or two, and a newer preview's push can cancel it); only the player page needs Pages and starts working once it has deployed. With no flow or shot tagged, the section is emptied, so a stale recording never stays in the description. A failing flow or shot does not block the preview; it shows up as "not recorded" or "not taken" and in the E2E check. Rules for flow specs are in `docs/coding-guidelines.md` §3.

### Review aids

- **Key changes and review map**: the PR template's sections that show the main API/code changes as snippets and tell the reviewer what to read first, which rules changed, which architecture section moved and the decisions left to them, as links rather than prose (coding guidelines §7). Claude fills them in when it opens a PR.
- **`REVIEW.md`**: what a reviewer flags as blocking, flags as optional, or ignores. The `pr-reviewer` subagent (`.claude/agents/pr-reviewer.md`) applies it in the session that opens the PR, in a fresh context, and the session posts its summary and inline comments on the PR. It runs on the session's subscription, so it costs nothing per review; the `claude-review` label runs the same check in CI when wanted.
- **`.gitattributes`**: the lockfile, changelog, release manifest and `docs/tasks/done/` are marked `linguist-generated`, so GitHub collapses them in the diff.

## On `main`

- **Deploy** (`deploy.yml`): builds and publishes to the root of the `gh-pages` branch → https://macandy13.github.io/arkham-companion/
- **PR sync** (`pr-sync.yml`): on every push to `main`, and whenever a PR branch moves, test-merges each open PR's base into its head. A conflict labels the PR `needs-rebase` and comments the conflicting files once; the Claude session watching the PR then merges `main` in and resolves them. A clean merge removes the label, and is pushed only when the optional repo secret `PR_SYNC_TOKEN` exists (pushes with `GITHUB_TOKEN` start no CI, which would leave the required checks missing). Skips forks, Dependabot and Release Please branches.
- **Open PR** (`open-pr.yml`, run by hand or by a session): opens a PR from an already pushed branch as the repo's GitHub App bot, assigned to the owner with the owner's review requested. Sessions reach GitHub only with the owner's credentials (a different token sent from a session is replaced on the way out), so this is how their PRs get an author other than the owner, which lets the owner approve them. It uses an App token because PRs opened with `GITHUB_TOKEN` start no workflows. Later pushes, edits and comments from sessions still appear as the owner. Fails with a notice when the App credentials are missing.
- **Review queue**: GitHub's own list of PRs waiting for the owner's review, [`review-requested:@me`](https://github.com/macandy13/arkham-companion/pulls?q=is%3Apr+is%3Aopen+draft%3Afalse+review-requested%3A%40me+sort%3Acreated-asc) (on the phone: GitHub app → Pull requests → Review requests). `open-pr.yml` requests the owner's review on every PR it opens; submitting a review takes the PR off the list, and the session that owns the PR requests it again once it has addressed the comments, which puts it back. Approved PRs wait for the merge under [`review:approved`](https://github.com/macandy13/arkham-companion/pulls?q=is%3Apr+is%3Aopen+review%3Aapproved). The list doesn't wait for green checks: a PR whose CI is red shows a red cross there, and its session is already fixing it.
- **Release Please** (`release.yml`): keeps a release PR with version bump and `CHANGELOG.md` from the Conventional Commit titles. Merging it tags the release. Release PRs are opened by the Actions bot, so CI does not run on them – merge them with the admin bypass.
  - **Versions stay below 1.0 until the app is declared ready by hand.** `release-please-config.json` sets `"versioning": "always-bump-patch"`, so every release bumps only the patch number, whatever the commit types (a `feat!` too). A new minor version (0.2.0, 0.3.0 …) and 1.0.0 are chosen by hand when a version step in [product.md](product.md#versions) is reached: add `"release-as": "<version>"` to the config in a PR, merge the release PR it produces, then remove `release-as` again (otherwise every later release keeps that version).

## Weekly

- **Dependabot** (`.github/dependabot.yml`): Monday, grouped npm minor/patch, npm major and GitHub Actions updates. CI checks them; merge when green.
- **CodeQL** scheduled scan.
- **Docs sync** (a Claude routine, configured at claude.ai/code/routines): compares merged PRs with the task issues and `docs/architecture.md`, opens a `docs:` PR for architecture drift and a sub-issue per unhandled follow-up under its task.

## Inside Claude Code sessions (`.claude/`)

- **SessionStart hook**: installs dependencies in fresh sessions.
- **Stop hook**: runs typecheck, lint and tests when code changed; failures go back to Claude to fix.
- **Subagents**: `rules-checker` (game rules vs. code, read-only), `pr-reviewer` (the branch against `REVIEW.md`, read-only) and `test-writer` (missing tests).
- **Auto-fix**: for PRs opened from a cloud session, turn on Auto-fix in the session's CI bar (or tell Claude "watch this PR and fix CI failures") so it fixes failing checks on its own.

## Repository settings (one-time, by the owner)

- Pages → Source: **Deploy from a branch**, `gh-pages` / root.
- Actions → General → **Allow GitHub Actions to create and approve pull requests** (Release Please).
- Merge button: **squash merging only**, default commit message **Pull request title**; auto-delete head branches.
- Optional: secret **`PR_SYNC_TOKEN`**, a fine-grained token for this repo with Contents and Workflows: read and write (a merge of `main` can bring in workflow changes), so PR sync pushes clean merges of `main` (each push runs the PR's full CI).
- GitHub App for PR authorship (`open-pr.yml`): created under the owner's account with no webhook, repository permissions Pull requests and Issues: read and write, Contents: read, installed on this repo only. Its App ID is the repo variable **`CLAUDE_BOT_APP_ID`**, its private key (the whole `.pem`) the secret **`CLAUDE_BOT_PRIVATE_KEY`**.
- Ruleset on `main`: require PR with 1 approval, require status checks `check`, `e2e`, `title`; block force pushes; admins may bypass (for release PRs). Leave _Require approval of the most recent reviewable push_ off: session pushes arrive as the owner, so it would reject the owner's own approval. A PR the owner authored (opened without `open-pr.yml`) can't be approved and is merged with the admin bypass.
