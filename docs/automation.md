### Screencasts

UI changes are easier to review as a recording than as a diff, and the preview workflow picks what to show by itself: nothing is tagged. `pnpm e2e:pictures` runs every spec fast and photographs it as it ends, once the screen has settled (the `endPicture` option of `e2e/fixtures/test.ts`: nothing fetched for 300 ms, pictures decoded, fonts loaded, animations stopped and reduced motion; every E2E page also draws a fixed `Math.random` sequence, so a skill test draws the same token every run): the flows (every spec outside `apps/web/e2e/shots/` but the accessibility checks) in the `flow-picture` project on the landscape tablet, and the screenshot specs (`apps/web/e2e/shots/`) in the `screenshot` project on the tablet and in `screenshot-phone` on a phone in portrait (390×844, the size the phone play screen is designed for). `main-pictures.yml` runs it on every push to `main` (checked out under `base/`, in three shards whose reports and pictures a save job joins into one entry, and only when all three reported) and keeps the report and pictures in an Actions cache keyed by the git trees they are made from (`apps/`, `packages/`, the lockfile, the E2E setup and the photographing workflow: `.github/actions/main_pictures`), so a commit that changes only docs or other workflows reuses the entry before it and runs nothing (and an entry is never photographed again, so a spec that failed there by chance stays shown until those trees change). Every commit on main gets its run (none cancels another, or a busy main would leave most commits without an entry). The preview's `base-cache` job looks that entry up for the PR's base (the merge commit's first parent), waiting up to 8 minutes (a sharded main run takes about 4) while main's run for that commit is still photographing; only when there is none (it failed, or took longer) does `pictures-base` photograph the base itself (a second checkout under `base/`, with its own install and its own `e2e:pictures` script, so it photographs with the projects the base has). `pictures-head` photographs the PR. Both picture jobs are split over three runners (`--shard=n/3`), each on every core (`--workers=100%`), and each shard uploads its report (`screencasts/pictures/<n>.json`) and pictures as an artifact; every picture job shows the same mock card art (see E2E above), so the base and the PR never differ by what a runner managed to download. Each picture shown also leaves the PR's copy, the base's and pixelmatch's difference map under `pr-preview/pr-<n>/screencasts/diff/`; the `preview` job restores the cache or unpacks the artifacts where the pictures were taken (the reports name them by absolute path; setup shared in `.github/actions/e2e_setup`), `cli.ts` joins the reports of a directory, and `cli.ts` compares each spec's last picture on both sides with `pixelmatch` at Playwright's default tolerance, allowing up to 20 differing pixels for antialiasing (the playmat's faint lines differ by a few pixels between runs). A screenshot spec shows when its picture differs on any device; a flow is shown when its end state differs, so a flow whose only change is in its middle is not caught, a spec the base doesn't photograph (new, or failed there) always shows, and a device where the spec fails on both sides counts as unchanged. `cli.ts flows` turns the changed flows, at most `SCREENCAST_LIMIT` (5, since a change to something every screen shows changes nearly every flow), into a `--grep` pattern, and `pnpm e2e:screencast` re-runs just those in the `screencast` project with `slowMo` of 250 ms and video on, with a pointer and a highlight drawn on every interaction and the current `test.step` name as a caption (`video.show`); the changed flows past the limit are listed by name. `cli.ts render` converts each passing recording into a GIF (one frame per 250 ms step, each held 4 times as long, so it plays 4× slower than recorded; 800 px wide) plus the original WebM, adds a player page (`player.html`, with this push's flows written in, so its link can only pick one of them and never names a URL) that plays the WebM with pause, step-wise seeking and a speed choice starting at 0.25×, copies the changed screenshots next to them (`<slug>-desktop.png`, `<slug>-phone.png`) and renders the Markdown section: "Screenshots" first, desktop and phone side by side in an HTML table (widths 560 and 180, so both are about the same height; a device whose run failed gets "not taken" in its cell; `RECORDING_PROJECTS` names the projects and `SHOT_DEVICES` the devices, so each picture is read from its own project), then "Screencasts", each GIF linking the player. Flows stay tablet only. The preview workflow publishes them under `pr-preview/pr-<n>/screencasts/` and replaces the section between `<!-- screencasts:start -->` and `<!-- screencasts:end -->` in the PR description (appending it if the markers are missing). Text outside the markers is never touched. The section links its pictures (GIFs and PNGs) from the gh-pages commit just pushed on `raw.githubusercontent.com` (a commit, since the raw host caches branch URLs for 5 minutes whatever their query string), which serves them as soon as the workflow has pushed, so the description is updated right away instead of after the Pages build (a minute or two, and a newer preview's push can cancel it); only the player page needs Pages and starts working once it has deployed. When the PR changes no picture, the section is emptied, so a stale recording never stays in the description. A failing flow or shot does not block the preview; it shows up as "not recorded" or "not taken" and in the E2E check. Rules for flow and screenshot specs are in `docs/coding-guidelines.md` §3.

### Review aids

- **Key changes and review map**: the PR template's sections that show the main API/code changes as snippets and tell the reviewer what to read first, which rules changed, which architecture page changed and the decisions left to them, as links rather than prose (coding guidelines §7). Claude fills them in when it opens a PR.
- **`REVIEW.md`**: what a reviewer flags as blocking, flags as optional, or ignores. The `pr-reviewer` subagent (`.claude/agents/pr-reviewer.md`) applies it in the session that opens the PR, in a fresh context, and the session posts its summary and inline comments on the PR. It runs on the session's subscription, so it costs nothing per review; the `claude-review` label runs the same check in CI when wanted.
- **`.gitattributes`**: the lockfile, changelog, release manifest and `docs/tasks/done/` are marked `linguist-generated`, so GitHub collapses them in the diff.

## On `main`

- **Deploy** (`deploy.yml`): builds and publishes to the root of the `gh-pages` branch → https://macandy13.github.io/arkham-companion/
- **PR sync** (`pr-sync.yml`): on every push to `main`, and whenever a PR branch moves, test-merges each open PR's base into its head. A conflict labels the PR `needs-rebase` and comments the conflicting files once; the Claude session watching the PR then merges `main` in and resolves them. A clean merge removes the label, deletes the conflict comments and is not pushed: a clean PR squash-merges as it is, and pushing main into every open PR would re-run all their checks after each merge. Skips forks, Dependabot and Release Please branches.
- **Open PR** (`open-pr.yml`, run by hand or by a session): opens a PR from an already pushed branch as the repo's GitHub App bot, assigned to the owner with the owner's review requested. Sessions reach GitHub only with the owner's credentials (a different token sent from a session is replaced on the way out), so this is how their PRs get an author other than the owner, which lets the owner approve them. It uses an App token because PRs opened with `GITHUB_TOKEN` start no workflows. Later pushes, edits and comments from sessions still appear as the owner. Fails with a notice when the App credentials are missing.
- **Review queue**: GitHub's own list of PRs waiting for the owner's review, [`review-requested:@me`](https://github.com/macandy13/arkham-companion/pulls?q=is%3Apr+is%3Aopen+draft%3Afalse+review-requested%3A%40me+sort%3Acreated-asc) (on the phone: GitHub app → Pull requests → Review requests). `open-pr.yml` requests the owner's review on every PR it opens; submitting a review takes the PR off the list, and the session that owns the PR requests it again once it has addressed the comments, which puts it back. Approved PRs wait for the merge under [`review:approved`](https://github.com/macandy13/arkham-companion/pulls?q=is%3Apr+is%3Aopen+review%3Aapproved). GitHub's lists don't show a PR's base, so `open-pr.yml` labels a PR stacked on another one `stacked` and puts a "Stacked on #n" line at the top of its description, below the attribution block; adding `base:main` to the filter leaves the PRs that can merge now (each stack's bottom). `pr-unstack.yml` takes the label off when GitHub retargets the PR to `main`. The list doesn't wait for green checks: a PR whose CI is red shows a red cross there, and its session is already fixing it.
- **Release Please** (`release.yml`): keeps a release PR with version bump and `CHANGELOG.md` from the Conventional Commit titles. Merging it tags the release. Each push to `main` waits an hour before Release Please runs, and a newer push cancels the waiting run, so the release PR is opened, refreshed or tagged only once `main` has had no push for an hour. Starting the workflow by hand (Actions → Release → Run workflow) skips the wait. Release PRs are opened by the Actions bot, so CI does not run on them – merge them with the admin bypass.
  - **Versions stay below 1.0 until the app is declared ready by hand.** `release-please-config.json` sets `"versioning": "always-bump-patch"`, so every release bumps only the patch number, whatever the commit types (a `feat!` too). A new minor version (0.2.0, 0.3.0 …) and 1.0.0 are chosen by hand when a version step in [product.md](product.md#versions) is reached: add `"release-as": "<version>"` to the config in a PR, merge the release PR it produces, then remove `release-as` again (otherwise every later release keeps that version).

## Weekly

- **Dependabot** (`.github/dependabot.yml`): Monday, grouped npm minor/patch, npm major and GitHub Actions updates. CI checks them; merge when green.
- **CodeQL** scheduled scan.
- **Docs sync** (a Claude routine, configured at claude.ai/code/routines): compares merged PRs with the task issues and `docs/architecture.md` with its component pages in `docs/architecture/`, opens a `docs:` PR for architecture drift and a sub-issue per unhandled follow-up under its task.

## Inside Claude Code sessions (`.claude/`)

- **SessionStart hook**: installs dependencies in fresh sessions.
- **Stop hook**: runs typecheck, lint and tests when code changed; failures go back to Claude to fix.
- **Subagents**: `rules-checker` (game rules vs. code, read-only), `pr-reviewer` (the branch against `REVIEW.md`, read-only) and `test-writer` (missing tests).
- **Auto-fix**: for PRs opened from a cloud session, turn on Auto-fix in the session's CI bar (or tell Claude "watch this PR and fix CI failures") so it fixes failing checks on its own.

## Repository settings (one-time, by the owner)

- Pages → Source: **Deploy from a branch**, `gh-pages` / root.
- Actions → General → **Allow GitHub Actions to create and approve pull requests** (Release Please).
- Merge button: **squash merging only**, default commit message **Pull request title**; auto-delete head branches.
- GitHub App for PR authorship (`open-pr.yml`): created under the owner's account with no webhook, repository permissions Pull requests and Issues: read and write, Contents: read, installed on this repo only. Its App ID is **`CLAUDE_BOT_APP_ID`** (a repo variable or secret), its private key (the whole `.pem`) the secret **`CLAUDE_BOT_PRIVATE_KEY`**.
- Ruleset on `main`: require PR with 1 approval, require status checks `check`, `e2e`, `title`; block force pushes; admins may bypass (for release PRs). Leave _Require approval of the most recent reviewable push_ off: session pushes arrive as the owner, so it would reject the owner's own approval. A PR the owner authored (opened without `open-pr.yml`) can't be approved and is merged with the admin bypass.
