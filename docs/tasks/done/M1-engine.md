## M1.1 Card definitions inside the engine (O)

**Why:** Rules need card numbers (doom threshold, shroud, enemy health), but the engine must stay pure and cannot load files. Passing a `CardDb` in a context object keeps it pure and lets tests use small fakes.

**Benefit:** Every rule module looks up card stats the same way, and per-investigator scaling ("2 per investigator") lives in one place.

Ref: §5, §9. The engine must read card stats (doom threshold, clues, shroud, health, keywords) without depending on `carddata` at runtime.

- [x] `CardDb` interface passed into `handle(ctx, state, command)` (`ctx.cards.get(code)`); reducer stays card-agnostic
- [x] Per-investigator value helper (`ScaledValue` + `resolveValue`, covers `health_per_investigator`/`clues_fixed`)
- [x] Fake `CardDb` fixture shared by all engine tests (now `test/utils/cards.ts`)

Done when: existing tests pass with the new signature; one test reads a threshold through `CardDb`.

Done: `packages/engine/src/cards.ts` adds `CardStats` (the engine's own card type, so it has no runtime dependency on `carddata`), `CardDb`, `EngineContext`, `cardDbFrom` and `cardStats` (throws `unknownCardCode`). `CardStats` is typed: `typeCode: CardType` (union of ArkhamDB type codes, `CARD_TYPES`), `traits: Trait[]` (branded, built with `trait`), `stage: CardStage` (`{ number, variant? }`, so alternative cards like 2a/b vs 2c/d share a number and differ by variant), and `clues`/`health`/`doom` are `ScaledValue`s (`{ fixed, perInvestigator }`) resolved with `resolveValue(value, playerCount)`. Game-state terms like "+1 per act" are left to the rules that read them. `handle(ctx, state, command)` and `execute(ctx, state, command)` take the context first; `StartScenario` rejects card codes missing from `ctx.cards`. Shared fixture: moved in M1.2 to `packages/engine/test/utils/cards.ts` (`testContext`, `testCardDefs`).
Follow-ups: map carddata's `CardDef` to `CardStats` (`health`/`health_per_investigator`, `clues`/`clues_fixed` → `ScaledValue`, `stage` → `CardStage`, `type_code` → `CardType`) when the web app gets a `CardDb` backed by the cached carddata (M2); the stage variant letter is not in ArkhamDB and has to come from scenario data; `keywords` gets added to `CardStats` with the keyword parser (M1.7).

## M1.3 Board: connection graph (S)

**Why:** Investigator movement, hunter enemies and many card effects depend on which locations connect. An explicit graph (not positions on screen) handles one-way edges, several maps and connections that change during play.

**Benefit:** Correct movement and pathing; the map UI in M3 only has to draw the graph.

Ref: §5 Map model.

- [x] `Edge` type (undirected and one-way), `ConnectionChanged` event, `AddConnection`/`RemoveConnection` commands
- [x] Connections from scenario data (`connections` spec by symbol or code), only active when both locations are in play
- [x] Reveal location (`CardFlipped`) places clues per investigator
- [x] Helpers: `neighbours(locationId)`, `shortestPaths(from, to)` (BFS, returns all shortest paths)
- [x] Multiple maps: locations carry `mapId`; cross-map edges allowed

Done: events `ConnectionChanged` (`added`/`removed`, with the owning `mapId` and the stored edge) and `CardFlipped`; commands `AddConnection` (names the owning `mapId`), `RemoveConnection` (finds the owner itself) and `RevealLocation` (`CardFlipped` + a `TokensChanged` for the clues, resolved with `resolveValue` like setup does). Edges live on `GameMap.connections`; the reducer updates the owning map. Cross-map edges are allowed and stored on exactly one map, the one named by the command (setup: the map whose `addMap` step declares it); ends may be on any map and movement ignores the owner, so `locationOnOtherMap` is gone. Undirected edges match either direction, one-way edges exactly; duplicates (also across maps), self-loops and unknown edges are rejected. Ends only have to be location cards by type, wherever they currently are, so set-aside locations can be connected. `board.ts`: `neighbours`, `shortestPaths` (BFS, all shortest paths) and `allConnections`; they only follow edges whose ends are both in a `location` zone (`isLocationInPlay`). `checkInvariants` checks edges name known cards and are unique. Tests: `board.test.ts` (`it.each` tables) with `startBoard`/`edge`/`runFrom` in `test/utils/board.ts`.
Follow-ups: `MoveInvestigator` (M1.4) should reveal an unrevealed destination via `RevealLocation`; `moveInvestigators` at setup could emit `RevealLocation` instead of flipping at compile time once setup can produce follow-up commands; the `connections` spec by symbol is still by code (symbol data comes with the M2 pipeline); removing or replacing a location card does not yet drop its edges (decide with the `replaceLocation`/`removeLocation` setup steps).

**Why:** The app replaces health/sanity dials and clue/resource piles, and enemy rules (prey) need to compare investigators.

**Benefit:** Fewer physical tokens, automatic defeat detection, and prey choices the engine can compute.

Ref: §5 `Investigator`.

- [x] `MoveInvestigator`, `AdjustInvestigator` (damage, horror, clues, resources), `DiscoverClues` (location → investigator)
- [x] Defeat check when damage ≥ health or horror ≥ sanity → `InvestigatorDefeated`, status `defeated`
- [x] Prey helpers: lowest remaining health/sanity, most clues, etc.

Done: Investigators already carry `health.max`/`sanity.max` in state (from the definition at `StartScenario`), so no new fields. Commands `MoveInvestigator`, `AdjustInvestigator`, `DiscoverClues`; events `InvestigatorMoved`, `InvestigatorChanged` (`stat` + `delta`), `InvestigatorDefeated` (`cause`). Movement needs a `neighbours` connection; `ignoreConnections` (for "move to any location" card effects) skips only that check, the destination must still be a location in play. An investigator without a location can be placed anywhere. ## M1.5 Agenda, act and doom (S)

**Why:** Doom and the agenda/act decks are the clock of every scenario. Summing doom by hand is easy to get wrong once doom sits on several cards (agenda, enemies, locations, player cards), so the app keeps the running total. Doom on player cards matters too, but the app does not model player cards – so each investigator gets a plain doom counter that counts toward the total. The engine asks before advancing instead of advancing silently ("assistant, not referee", §2).

**Benefit:** The app tells players when the agenda or act should advance and what happens next; a scenario ends with a resolution the campaign can record.

- [x] `PlaceDoom` (on agenda or any card), doom total = agenda + cards in play + each investigator's player-card doom counter
- [x] Per-investigator doom counter for doom on player cards the app does not track (`Investigator.doomOnPlayerCards`, adjusted via `AdjustInvestigator`)
- [x] Threshold check emits a `DecisionRequested` "advance agenda?" instead of advancing silently
- [x] `AdvanceAgenda` / `AdvanceAct`: flip, run reverse-side hook, next card; clue threshold per investigator for act
- [x] Scenario end hooks when the last agenda/act advances (`ScenarioEnded` with resolution id)

Done: `Investigator.doomOnPlayerCards` (new required field) is an `InvestigatorStat`, so `AdjustInvestigator` adjusts it. `doom.ts`: `isInPlay` (any card, by zone; not to be confused with the private location-only `isLocationInPlay` in `board.ts`; of the agenda/act decks only the current card is in play), `doomInPlay` (cards in play incl. agenda + counters of active investigators only), `agendaThresholdDecision`/`withAgendaCheck`. New commands `PlaceDoom` (current agenda by default; positive amount; card must be in play), `AdvanceAgenda`, `AdvanceAct` (paying clues is only one way to advance an act: with `spend`, who pays - the total must equal the act's printed clues resolved with `resolveValue` for the starting player count, and an act without a clue value rejects payment (`noClueThreshold`); without `spend` any act advances for free, for objectives, actions or events that players or M1.6 hooks decide); events `DecisionRequested`, `AgendaAdvanced`, `ActAdvanced`, `ScenarioEnded` (`GameMeta.resolution`). `ScenarioStarted` now sets `agenda.current`/`act.current` to the top of each deck. After `PlaceDoom` or a `doomOnPlayerCards` adjustment that reaches the threshold, a `DecisionRequested` of kind `advanceAgenda` is added to `pending` (id `advanceAgenda:<agendaId>`, not repeated while open); `Decision` gained an optional `subject`, and advancing drops decisions about the old card. Advancing flips the card, moves it to `outOfGame`, makes the next card current; `AdvanceAgenda` also removes all doom in play. The last card of a deck needs `resolution` and then emits `ScenarioEnded`. The reverse-side hook is the no-op `reverseSideEvents` in `handle_scenario.ts`. The agenda threshold is a `ScaledValue` resolved with `resolveValue` like the act's clues. Tests: `doom.test.ts` (example tests on `testContext` plus an `it.each` table for the doom-total invariant: agenda + cards in play + investigators' counters).
Missing thresholds stay `undefined` (never 0): an agenda without `doom` never asks to advance, an act without `clues` cannot be paid for. `requireCard` (`lookup.ts`) is the shared "known card or `unknownCard`" lookup used by all handlers.
Review points solved in later PRs: doom on cards advancing the agenda by itself (#31, M1.10: explicit `CheckDoomThreshold`) and the instructions on the flipped act/agenda (M1.6 scenario hooks).
Review fixes (macandy13): new package `@arkham/util` (`packages/util`, `string.ts`: `stripTrailingDot`), a dependency of the engine; `comparableName` (`cards.ts`) is `stripTrailingDot(text.trim()).toLowerCase()` and is used for spawn names and prey criteria. Shared lookups next to their entity: `cardsOfType`/`cardsNamed` (`lookup.ts`), `locationsInPlay`/`locationsNamed(ctx, state, name, { inPlay? })` (`board.ts`); spawn, `startingEngagements` and hunters use them. `MoveHunters` no longer moves everything in card order: no mover -> no events, one mover -> it moves, two or more -> `hunterOrder` decision (kind `chooseCard`, `decider: { kind: 'lead' }`, one option per mover, id and target = hunter ID; Rules Reference "Hunter" and "Lead Investigator"). `MoveHunters` got an optional `hunters` list. **M1.9 must wire:** the `hunterOrder` option for hunter X runs `MoveHunter { enemyId: X }` and then `MoveHunters { hunters: <the other options' IDs> }` (the list stops a hunter that already moved from moving again; the second command asks again if two or more still move). `Decision.decider` is optional here with `Decider = lead | group`; M1.9 makes it required and adds the `investigator` variant and option `commands`.
Follow-ups: M1.9 `ResolveDecision` must turn "yes" into `AdvanceAgenda` and clear the decision (declining currently leaves it pending; no re-ask until it is cleared); M1.6 plugs the reverse-side hook into `reverseSideEvents` and uses it to apply `theGatheringHouse` when act 1 advances (needs mid-scenario setup steps, taking the locations from the set-aside zone) – done in M1.6 (`onActAdvance`, `compileMapStep`, `AddMap`); the threshold check runs after every doom placement, not only in the mythos phase - M1.10 should gate it; `ManualAdjust` doom changes do not run the check; the resolution id comes from the caller until agenda/act reverse sides are data; commands after `ScenarioEnded` are not blocked yet; `ManualAdjust` can still move the current agenda/act out of its deck; rules to double-check: removing all doom on every agenda advance (also card-effect advances) and ignoring defeated investigators' doom counters.

## M1.6 Triggers and hooks (O)

**Why:** Forced effects ("after doom is placed…", "when this agenda advances…") are how scenarios bend the rules. A generic trigger bus lets scenarios plug in without changing engine code.

**Benefit:** Scenario-specific mechanics stay in scenario files; the loop guard prevents a bad hook from hanging the app.

Ref: §6 Triggers, §7 hooks.

- [x] Trigger bus: after events are produced, hooks (`afterDoomPlaced`, `onAgendaAdvance[code]`, `onActAdvance[code]`, `onRoundEnd`, `onCardEnters`) may return follow-up commands
- [x] Hooks are pure functions `(ctx, state, event) -> Command[]`; the bus runs each returned command through `handle` like a player command, so hook effects are validated and can use card data and the RNG the same way (returning raw events would bypass both). Loop guard against infinite chains
- [x] Effects registry keyed by card code (empty except a sandbox card that adds a connection; now a test-only effect, see Done)

Done: `packages/engine/src/triggers.ts` adds `TriggerHook<E>` (`(ctx, state, event) -> Command[]`; the triggering event is passed so a hook knows which card/amount fired it), `ScenarioHooks` (`afterDoomPlaced` on every positive doom `TokensChanged`, `onAgendaAdvance[code]`/`onActAdvance[code]` on `AgendaAdvanced`/`ActAdvanced`, `onCardEnters` on a `CardMoved` from outside play into play, `onRoundEnd` declared only), `CardEffect` (`onReveal` on `CardFlipped` face up), `EffectsRegistry` and `MAX_TRIGGERED_COMMANDS` (50). Hooks and effects reach the engine through `EngineContext.hooks`/`effects` (code, so not in the serialisable state); `ScenarioDefinition.hooks` holds a scenario's hooks for the app to pass in. The bus lives in `handle`: after a command's events, `triggeredCommands` collects the matching hooks (matched per event, evaluated on the state after all of the command's events; order = event order, scenario hooks before card effects) and each follow-up is handled like a player command, depth first, its events appended to the same list. **Grouping:** one player command returns one event list including its whole forced-effect chain, so M1.11 can undo it as one group. `ManualAdjust` and `StartScenario` fire no triggers (corrections and setup are not game events). A rejected follow-up rejects the originating command with `triggeredCommandRejected` (innermost command type + reason); more than 50 follow-ups in one chain reject it with `triggerLoop`; `execute` stays atomic, so the state is unchanged either way. The M1.5 no-op `reverseSideEvents` is gone; the reverse side is now the `onAgendaAdvance`/`onActAdvance` hook. **Reverse-side order (rules review fix):** advancing runs in two steps inside one command – (agenda: doom removal,) `CardFlipped` + `AgendaAdvanced`/`ActAdvanced` (the hook fires here and sees the advancing card still current), then, after that chain, `completeAdvance` emits `CardMoved` (out of game) + `CurrentCardChanged` for the next card. On the last card the hook ends the scenario by returning the new `EndScenario` command; the command's `resolution` is only a fallback when no hook did, and is rejected (`unexpectedResolution`) while cards remain. Effects registry: the sandbox card effect (revealing a location connects it to a set-aside one) did not survive the switch to the Gathering test scenario, which has no such card; it is now a test-only effect in `triggers.test.ts`, so no scenario ships an `EffectsRegistry` yet. **The Gathering act 1 (first real hook):** `theGathering.hooks.onActAdvance['01108']` (`trappedReverseSide` in `packages/scenarios/src/the_gathering/scenario.ts`) puts `theGatheringHouse` into play from the set-aside locations, discards the enemies in the Study (also those engaged with investigators there), moves every active investigator to the Hallway (`MoveInvestigator` with `ignoreConnections`, which reveals it) and removes the Study from the game. Two generic primitives were added for it: `AddMap` (`mapId`, `map: MapSpec`, `locations`: cards outside play that move onto the new map; produces the new `MapAdded` event, then a `CardMoved` per location, so `onCardEnters` fires; rejects `duplicateMap`, `cardAlreadyInPlay`, non-locations, repeated locations and connections already on the board) and `MoveCard` (`cardId`, `to`: the same move and validation as a `ManualAdjust` `moveCard`, but a game event, so forced effects fire). `compileMapStep(state, step)` (`setup.ts`) turns an `AddMapStep` into an `AddMap` against a running state (each code must match exactly one card outside play) plus a `RevealLocation` per `faceUp` location. Tests: `the_gathering.test.ts` (house layout, investigators in the revealed Hallway, Study out of game, enemies discarded, all before act 2 becomes current), `AddMap` in `board.test.ts`, `MoveCard` in `engine.test.ts`, `compileMapStep` in `setup.test.ts`. Trigger tests: `triggers.test.ts` (on `testContext`/`makeInvestigator`/`edge` from `test/utils`; the former property test is an `it.each` loop-guard table over chain length, fan-out and an invalid step: each case finishes within the guard or rejects with the state unchanged).
After merging M1.5's review: `AdvanceAct.spend` is optional, so a hook that advances an act on an objective returns `{ type: 'AdvanceAct' }` without `spend` (with `spend`, the act must have a clue threshold, else `noClueThreshold`); M1.6's handlers use `requireCard` and its tests the shared `stateAfter`/`rejectionFrom`/`startScenario` helpers.
Follow-ups: `onRoundEnd` fires once M1.10 emits a round-end event; `onCardEnters` is fed by `MoveCard` and `AddMap` so far – `DrawEncounter`/`SpawnEnemy` (M1.7/M1.8) must produce `CardMoved` into play too; removing a location (`MoveCard` to `outOfGame`) does not drop its connections or discard what is attached to it or at it (the Gathering's Study has neither by the time act 1 advances, apart from the enemies the hook discards) – decide with `removeLocation`; the Gathering's act 3 / agenda 3 reverse sides (resolutions via `EndScenario`) and the Ghoul Priest/Lita Chantler set-aside cards still need their hooks (later tasks); simultaneous forced effects run in a fixed order instead of letting the lead investigator choose (M1.9 `chooseOption` decision if a scenario needs it); forced effects that need confirmation ("apply a forced effect?", M1.9 `confirm`) are applied directly; a reverse side that ends the scenario still lets the deck move on (`CardMoved`/`CurrentCardChanged` follow `ScenarioEnded`) – revisit when commands after the end are blocked; sibling follow-ups are computed from the same snapshot, so a hook should not return several commands that depend on each other's effect; a skipped "resolve as much as possible" (rules) is up to the hook, the bus rejects instead of partially applying.

## M1.7 Encounter deck and mythos draw (S)

**Why:** The encounter deck is the main thing the app takes off the players' hands. Parsing keywords once at load time lets every rule module react to them consistently.

**Benefit:** No manual shuffling or drawing of the encounter deck; surge, peril and empty-deck reshuffles are never forgotten.

- [x] `DrawEncounter(investigator)`: top card → revealed; treachery → discard or threat area; enemy → spawn
- [x] Keyword parser (surge, peril, hunter, aloof, elite, massive, retaliate, alert, patrol, prey, spawn) from card text → `keywords` on `CardDef` at load time; victory X comes from the ArkhamDB `victory` field
- [x] Surge draws again; empty deck reshuffles discard
- [x] Matched draws (`DrawEncounter` with `match`/`from`), `fromSetAside(codes, to)`, `shuffleInto` primitives

Done: Keywords: `packages/carddata/src/keywords.ts` adds `parseKeywords(text, traits)` (surge, peril, hunter, aloof, massive, retaliate, alert, `patrol`/`prey`/`spawn` with their text as `detail`; `elite` comes from the traits) and `entersThreatArea(text)`; `normaliseCard` fills `CardDef.keywords`/`entersThreatArea` at load time. Only lines made up entirely of keyword sentences count, so body text cannot produce one; `<i>` reminder text is ignored. The engine mirrors the types (`Keyword`, `KeywordName`, `hasKeyword`) and `CardStats.keywords`/`entersThreatArea`. `DrawEncounter` (`handle_encounter.ts`): reveals the top card (`EncounterCardDrawn` with `peril`/`surge` flags for the UI, then `CardFlipped`, `CardMoved`); enemy -> `atLocation` of the drawer, unengaged (**boundary:** engagement, aloof and spawn instructions are M1.8's `SpawnEnemy`); treachery with `entersThreatArea` -> threat area; everything else -> top of the encounter discard (index 0, so "topmost" is the first entry). Surge draws again inside the same command (capped at the number of encounter cards so an all-surge deck ends). An empty deck is refilled by moving the discard over and a `DeckShuffled` (seeded, in the event). Cards entering play this way feed `onCardEnters` through the bus. `DrawEncounter { investigatorId; from?: 'deck' | 'discard' | 'deckOrDiscard'; match?: { name?, trait?, typeCode? }; discardSkipped? }` also covers searches: with `match` the first matching card (deck top-down, then discard top-down; `from` defaults to `deck`) is drawn through the same `drawOne` as the top card (revealed, placed by type, enemy via `spawnZone`, surge handled), rejecting with `noMatchingCard` when nothing matches; `discardSkipped` first discards the deck cards above the match ("discard until X, then draw it"). There is no separate discard-draw command. Gathering cards that need it: Rise of the Ghouls (agenda 01106: discard from the top until a Ghoul enemy, the lead investigator draws it = `match: {trait: Ghoul, typeCode: enemy}, discardSkipped: true`) and, on Hard/Expert, The Gathering's setup text (search deck and discard for a Ghoul enemy, `from: 'deckOrDiscard'`). Agendas/acts 01105 and 01107-01110, Ghoul Priest and Lita Chantler need no encounter-deck draw (set-aside and board changes only). Later Arkham sets use the same shapes (Arkham Woods, Into the Darkness, Mysterious Chanting), and _Fire!_ (Spreading Flames, M4) is `from: 'discard'` with a `name` match. New primitives: `FromSetAside {codes, to}`, `ShuffleInto {codes, zone}` (from set aside). Zone-reference validation and the shared `cardMoved` (the validated `CardMoved` used by `MoveCard`, `ManualAdjust` and the encounter handlers) live in `placement.ts`, so `handle.ts` and `handle_encounter.ts` share them without importing each other. ## M1.11 Undo and replay (S)

**Why:** Mis-taps happen constantly at the table, so undo is essential. With event sourcing it is just "drop the last command's events and replay".

**Benefit:** Any action can be undone safely, and because the RNG state is restored too, undo cannot be used to re-roll a shuffle.

- [x] Event log grouped by command (`commandId`), `Undo` removes the last group and replays from the latest snapshot
- [x] Readable `it.each` table instead of a property test (the repo prefers example tables): scripted command sequences, including turns, an allowance change and a revelation test → undo group by group → every earlier state, finally the empty state

Done: `StoredEvent.commandId` is shared by all events of one `appendEvents` call (= one `execute` result, i.e. one player command with its trigger chain); the store generates it (`crypto.randomUUID()`) unless the caller passes the new 4th parameter `commandId`, so the engine stays ID-free. `GameStore.undoLast(gameId, expectedSeq?)` deletes the last group, lowers `lastSeq`, deletes a snapshot beyond the new end (the single stored snapshot is by construction the latest one at or before it, otherwise replay starts from scratch) and returns the replayed `LoadedGame` (unchanged on an empty log, `undefined` for an unknown game). The pure part is `undoLastGroup(log)` in `packages/engine/src/undo.ts` (`{ kept, removed }`, generic over entries with a `commandId`). The RNG state lives in `GameState`, so undo restores it: `undo.test.ts` proves undo + redo of a `ShuffleInto` yields identical events and state; an `it.each` table of six scripted sequences (draws, token and move adjustments, shuffles, `NextPhase`, a decision asked and answered, a mix) undoes group by group and checks every intermediate state and finally the empty state (no fast-check; the former property test is gone). Groups follow M1.10: one `NextPhase` result (all steps, follow-ups and forced effects) is one group, `ResolveDecision` is its own group, and so is the `NextPhase` that resumes; the phase cursor (`meta.steps`, `meta.turnsTaken`) is state set by `PhaseChanged`/`PhaseStepsChanged`/`RoundEnded`/`TurnEnded`, so replay restores it. **Undo while a decision is pending is allowed:** undo is a store operation on the log, not a command, so `decisionPending` does not apply, and the pending decision is just state (`DecisionRequested`/`DecisionResolved`): undoing the group that raised it removes it, undoing the answer brings it back (tested). Tests use the shared `test/utils` (`contextWith`, `makeCard`, `makeInvestigator`). **With M1.10's state:** `meta.turn`, `meta.turnsTaken`, the phase step cursor, pending decisions and the `resolving` zone are all set by events, so replay restores them; `undo.test.ts` proves it (undoing an `AdjustActions` restores the counter, 2 -> 3, since the players count actions on `Investigator.actionsRemaining` after review #31; undoing a move taken mid-turn puts the investigator back; undoing `EndTurn` reopens the turn and clears `turnsTaken`; undoing the answer to a revelation test puts the treachery back in `resolving` with its decision pending) and that a move with the reveal of its destination, `TurnStarted` and `ActionsAdjusted` are in the group of their command, because `handle` returns them in the one list of one `execute`. Store tests in `IndexedDbStore.test.ts` (fake-indexeddb). Additive on `GameStore`/`IndexedDbStore` to ease the merge with M2.6/M2.7.
Follow-ups: no redo stack (redo = executing the command again, which is deterministic); events stored before this change have no `commandId` (the schema is unreleased, no migration); `undoLast` loads the whole log to find the last group (fine for table-sized games, could read the tail only); the UI (M3) must call `appendEvents` once per `execute` result and not split it; undoing is allowed past `ScenarioEnded`.

End-to-end test (M1.E), done: `TestTable` logs events with a `commandId` per `play` and has `undo()` (`undoLastGroup` on that log, then `replay`). In round 2 Roland's mis-tapped move to the Parlor is undone: he is back in the Hallway (the players had not counted the move off his counter yet, so only the location is checked); the final replay check still holds.

## M1.15 Investigator defeat and resign (S)

**Why:** Defeat only sets a status today. The rules also put the investigator's clues on their location, disengage their enemies, remove their threat-area cards and pass the lead on (M1.4 follow-up); `resigned` has no command. A defeat in the middle of a game leaves the board wrong.

**Benefit:** A defeated or resigned investigator leaves the table the way the rules say, so the rest of the group can keep playing on a correct board.

Ref: RR "Investigator Elimination"; M1.4, M1.8 follow-ups.

- [x] On defeat or resign: clues to the investigator's location, engaged enemies stay at that location unengaged, threat-area treacheries to the encounter discard
- [x] `Resign` command (an action, in the investigator's turn), status `resigned`, same clean-up as defeat
- [x] A defeated or resigned lead investigator: the group picks a new lead (`chooseInvestigator` decision)
- [x] All investigators defeated or resigned ends the scenario (`ScenarioEnded`, no resolution given → the scenario's "no resolution" hook)
- [x] Rules to check: a defeated drawer mid-mythos, doom on defeated investigators' cards
- [x] End-to-end test: an investigator resigns or is defeated in a later round

Done: `elimination.ts` holds `investigatorLeavesEvents(state, investigator, left)`, the one place every way out of the scenario goes through (`AdjustInvestigator` and `ResolveEnemyAttack` on a defeat, `Resign`). Events, in order: the departure (`InvestigatorDefeated` or the new `InvestigatorResigned`; the reducer sets the status and ends a turn in progress), then the clean-up as ordinary events (clues: `InvestigatorChanged` -n plus `TokensChanged` on the location, skipped for an investigator without a location; `EnemyDisengaged` for each engaged enemy, which keeps damage and exhaustion; `TokensChanged` removing the tokens of each threat-area card, then `CardMoved` to the top of the encounter discard, so doom does not return if the discard is reshuffled), then the succession. **Lead:** `GameMeta.leadInvestigator` was already stored; new event `LeadInvestigatorChanged` and command `SetLeadInvestigator {investigatorId}` (active investigators only, `alreadyLeadInvestigator` if unchanged; also usable for card effects). When the lead leaves and several investigators remain, a `chooseInvestigator` decision `newLeadInvestigator` (decider: group, no subject) has one `SetLeadInvestigator` option per remaining investigator; with a single one left they become lead directly. `playerOrder` keeps rotating from the old lead's seat until the new lead is set. **No one left:** `ScenarioEnded` without `resolution` (it is now optional); the engine has no scenario "no resolution" hook, so `GameMeta.resolution` stays absent and "ended" is not visible in the state (see follow-ups). **`Resign {investigatorId}`:** only in the investigation phase (`wrongPhase`), for an active investigator (`unknownInvestigator`, `investigatorNotActive`) whose turn is in progress (`turnNotInProgress`, shared with `EndTurn` via `requireTurnOf`); no new rejection code. The last turn of the investigation phase no longer waits for departed investigators (`playerOrder` only lists active ones). Tests: `elimination.test.ts` (`describe.each` over defeat by damage, by horror and resign: clues, enemy zone/tokens/exhaustion, threat area and doom, turn, invariants; lead decision and answer, single successor, non-lead leaving; last investigator; `Resign` and `SetLeadInvestigator` rejections; an enemy-attack defeat drops the other attacks of that investigator from step 3.3). The Gathering end-to-end test: in round 6 Wendy resigns with Frozen in Fear and a Swarm of Rats on her (`TestTable.resign`). Existing defeat tests in `investigators.test.ts` and `phases.test.ts` now also see the clean-up events. **Rules check (#45):** all interpretations hold; two loose ends fixed: an investigator without a location has nowhere to leave their engaged enemies, so those are discarded (an unengaged enemy must be at a location), and cards attached to a discarded threat-area card go to the encounter discard with it, tokens removed (`discardEncounterCard`).
Follow-ups: `ScenarioEnded` without a resolution leaves no trace in `GameMeta` (and commands after the end are still not blocked, M1.4 follow-up): add an `ended` marker when the end is enforced, and a scenario "no resolution" hook (The Gathering's guide names what follows when every investigator resigned or was defeated); the lead decision is not about a card, so it has no `subject` and `TestTable.answer` (which looks up by subject name) cannot answer it, scripts use `ResolveDecision` with `newLeadInvestigator`; rules to check: (1) a drawer defeated mid-mythos: their own encounter card stays in the `resolving` zone until its test is answered (the tests that defeat them are the card's own), and the remaining 1.4 draws skip them (`canDraw`), a surge draw of the defeated drawer is not special-cased; (2) doom on a defeated investigator's cards: treachery doom is removed with the discard, `doomOnPlayerCards` stays on the defeated investigator but no longer counts (`doomInPlay` counts active investigators only) and is not cleared; (3) clues of an investigator without a location stay with them; (4) a defeated lead during a phase step: the decision blocks further commands until answered, so `NextPhase` stops there like at any other decision; (5) player cards are not modelled, so the discarding of the investigator's own cards, weaknesses and the "remove from game" of story assets are left to the players.

## M1.19 Shared event building blocks (S)

**Why:** Several modules build the same basic events by hand: moving a card (`CardMoved` in board, placement, hunters, scenario and elimination code), removing every token from a card, moving clues between an investigator and a location, discarding a card with its attachments (review #45). Each copy can drift, and a module's intent is hidden behind event plumbing.

**Benefit:** Modules say what happens ("discard this treachery", "these clues go to the location") and share one correct way of doing it.

Ref: review #45 (`elimination.ts`). A `refactor:` PR with no behaviour change.

- [x] `moveCardEvent(card, to, index?)` next to the zones, used wherever `CardMoved` is built
- [x] `clearTokensEvents(card)` next to the cards (used by elimination and the doom removal in `handle_scenario.ts`)
- [x] `cluesToLocationEvents(investigator, locationId, amount)` next to `DiscoverClues`, its reverse
- [x] `discardEncounterCard(state, cardId)` (attachments first, tokens cleared) moved next to the cards

Done: the card builders live in `placement.ts`, where card moves already were (`zone.ts` only describes zones): `moveCardEvent(card, to, index?)` builds a `CardMoved` without validation, for moves the engine decides (hunters, maps, agenda/act advance, discards); the validating `cardMoved` used by commands now builds on it. `clearTokensEvents(card, tokens = TOKEN_KINDS)` removes every token of the given kinds; the agenda advance uses it with `['doom']`. `discardEncounterCard(state, cardId)` moved there from `elimination.ts` and was renamed from `discardEvents` (review #60: an "event" is also a player card type, and this only discards encounter cards). The clue builders live with the investigator in `investigators.ts`: `discoverCluesEvents` (used by `DiscoverClues`) and its reverse `cluesToLocationEvents` (used by elimination). No `CardMoved` is built by hand any more outside `placement.ts`. No behaviour change: event lists and their order are the same. Tests: `placement.test.ts` for the builders; the existing tests cover every caller.
